# Tinjauan rencana backend Rehat

Peninjau: kirocrew-worker (report-only). Dokumen ini hanya melaporkan temuan. Tidak ada keputusan, perubahan kode, commit, atau push yang dibuat, dan file `.env` tidak dibaca.

**Rencana yang ditinjau.** Backend dibangun di repo Next.js 16 + Bun + `server.mts` (ws) yang ada, menggantikan NestJS di dossier. Stack terkunci: Prisma, Supabase Auth, `/phone` tetap web. Fase F0 (schema, `.env.example`, helper Supabase, seed, tanpa DB hidup), F1 (auth 3 peran, invite caregiver sekali pakai, persetujuan), F2 (CRUD program + safety envelope), F3 (ingestion ringkasan sesi + breach event, `/screen` baca dari backend), F4 (eskalasi L2 pause + push FCM), F5 (Docker + CI). Diparkir: WhatsApp L3, deploy VPS, kredensial FCM/Supabase cloud.

**Sumber yang dibaca.** `Rehat_Dossier.pdf` (via pdftotext), `AGENTS.md`, `package.json`, dan untuk membuktikan temuan: `server.mts`, `src/lib/relay/rooms.ts`, `src/lib/relay/protocol.ts`, `src/lib/rehab/{envelope,session,summary,defaults,messages}.ts`, `src/hooks/usePhoneSession.ts`, `src/lib/db.ts`, `docs/NOTES.md`, `docs/TESTING.md`, `.gitignore`, `next.config.ts`, dan `node_modules/next/dist/docs/01-app/02-guides/custom-server.md`.

**Snapshot.** Bukti dibaca dari commit `ade193b` ditambah working tree saat tinjauan dimulai. Selama tinjauan, pohon kerja berubah oleh pihak lain (bukan peninjau): `package.json` kini menambah `@prisma/*`, `@supabase/*`, `prisma`; ada `prisma/schema.prisma`, `prisma.config.ts`, `docs/BACKEND-INTEGRATION.md` (tidak dibaca), dan `.gitignore` menambah `/src/generated/`. **Label.** FACT = terbukti dari file yang disebut. ASSUMPTION = belum saya verifikasi (perlu dicek tim sebelum dipercaya). Setiap temuan satu paragraf; urutan di dalam bagian tidak menunjukkan prioritas. Ini bukan nasihat hukum atau medis.

## 1. Premis yang salah atau belum terbukti

**P1. `docs/HANDOFF.md` tidak ada.** `AGENTS.md` memerintahkan membaca `docs/HANDOFF.md` "sebelum keputusan desain apa pun" dan menyebutnya sumber alasan di balik aturan. FACT: `ls docs/` hanya berisi `MODE2_RESEARCH.md`, `NOTES.md`, `PROTOTYPE_PROMPT.md`, `SENSORS.md`, `TESTING.md`. Rencana backend mengubah keputusan arsitektur (NestJS ke Next, JWT sendiri ke Supabase) tanpa dokumen alasan yang dirujuk aturan repo. Format "Options, Trade-offs, Recommendation, What would change it" dari `AGENTS.md` belum ditulis untuk penggantian ini.

**P2. "F4 eskalasi L2 pause" mengandaikan pause saat breach sudah ada. Belum ada.** Dossier (urutan kejadian breach sampai eskalasi) menaruh langkah "masih breach, L2: pause latihan" di HP. FACT: di `src/hooks/usePhoneSession.ts` (blok `if (r.breach)`) breach hanya memanggil `speak()` dan `vibrateCue()`. Di `src/lib/rehab/session.ts` fase `paused` hanya dicapai oleh sensor lost atau tombol manual (komentar "Not monitored = not safe: losing the sensor always pauses"). Server tidak bisa mem-pause HP selain lewat pesan yang harus diterima dan dijalankan edge. Jadi F4 bukan pekerjaan backend saja: perlu perubahan di aturan sesi HP, dan itu berada di jalur keselamatan.

**P3. `onBreach` dan `notifyCaregiver` belum ada di kode.** F2 menyimpan lima field envelope. FACT: `SafetyEnvelope` di `src/lib/rehab/envelope.ts` hanya punya `maxAngleDeg`, `maxVelDegPerS`, `debounceMs`; `grep` untuk `onBreach` dan `notifyCaregiver` di `src`, `tests`, `docs` tidak menemukan apa pun. Dua field yang disimpan terapis di dashboard tidak akan berefek di HP sampai edge membacanya. Risiko: terapis memilih "cue + pause" dan mengira terpasang, padahal HP hanya bersuara.

**P4. "`/screen` baca dari backend" mengandaikan `/screen` adalah dashboard terapis. Sekarang bukan.** FACT: `/screen` adalah layar laptop untuk pairing dengan kode ruang 4 digit tanpa akun (`server.mts`, `docs/NOTES.md` M0). Batas keselamatan hari ini berasal dari slider di `/screen` yang dikirim lewat relay sebagai pesan `config` (`ScreenPayloads` di `src/lib/rehab/messages.ts`). Dossier mendefinisikan dashboard terapis sebagai pembuat program, penentu batas per pasien, pembaca log dan penulis catatan. Fase F0 sampai F5 tidak memuat UI daftar pasien, plan builder, atau catatan terapis. Definisi "MVP selesai" di `AGENTS.md` (terapis membuat program + envelope, lalu melihat log dan menulis catatan) tidak dapat dicapai oleh F0 sampai F5 sebagaimana ditulis.

**P5. `/phone` tetap web berarti bagian mobile di dossier harus diganti, dan rencana tidak menyebutnya.** Dossier: mobile React Native (Expo dev build), token di Keychain/Keystore (`expo-secure-store`), push lewat `@react-native-firebase/messaging`, SQLite untuk outbox. ASSUMPTION (perlu dicek tim): FCM di web butuh service worker, VAPID key dan HTTPS; pada iPhone, web push umumnya hanya jalan bila situs dipasang ke Home Screen. Caregiver Level 1 di dossier adalah aplikasi mobile; rencana tidak menyebut permukaan mana yang menerima push L2 (halaman web baru? PWA?). Tanpa itu F4 tidak punya penerima.

**P6. Prisma tidak mengelola tabel `auth.users` milik Supabase.** ASSUMPTION: `Profile` harus punya id yang sama dengan `auth.users.id`. Rencana tidak menyebut cara membuatnya (trigger, atau saat login pertama) dan cara menghapusnya. Kalau akun auth dihapus tetapi `Profile` dan data sesi tinggal, hak hapus data (bagian 4) tidak terpenuhi.

**P7. "Tanpa DB hidup" di F0 berarti schema dan seed tidak pernah dijalankan.** `prisma validate` dan `prisma generate` bisa jalan tanpa DB, tetapi SQL migrasi, constraint, dan seed tidak teruji sampai ada database. Catatan memori proyek lain milik pemilik mencatat masalah Prisma + pooler Supabase (URL pooler untuk runtime, koneksi langsung untuk migrasi); ASSUMPTION bahwa hal serupa berlaku di sini, dan F0 tidak menyebut `directUrl`.

## 2. Kelemahan rencana

**K1. Kontrol keamanan NestJS di dossier tidak punya pengganti di Next.** Dossier (Arsitektur backend) mendaftar lapisan global: Helmet, CORS ketat, ValidationPipe whitelist, Throttler, JwtAuthGuard, RolesGuard, CareRelationGuard, audit interceptor. Route handler Next.js tidak menyediakan padanannya. FACT (di `ade193b`): `package.json` tidak punya library validasi skema atau rate limiter, dan belum punya Prisma/Supabase; semuanya dependensi baru, dan `AGENTS.md` meminta dependensi jaringan baru ditandai sejak awal. Tanpa lapisan bersama, tiap route handler harus mengulang cek auth, relasi, validasi, rate limit, dan audit; satu route yang lupa jadi lubang BOLA.

**K2. `proxy.ts` (pengganti middleware) bukan batas otorisasi.** FACT: dokumentasi Next 16 di repo (`proxy.md`) menyebut Proxy dijalankan terpisah dari kode render dan, pada kasus optimal, dapat berjalan di CDN, sehingga tidak boleh mengandalkan modul atau global bersama. Cek peran dan relasi pasien harus ada di tiap route handler atau data layer, bukan hanya di proxy.

**K3. Entitas F0 tidak mencakup alur inti dossier.** Daftar F0: Profile, CaregiverInvite, Program, Exercise, SafetyEnvelope, RehabSession, AttemptSummary, BreachEvent, Alert. Dossier (Model domain, Skema data) juga mensyaratkan: `CareLink` (pending/active/revoked + `consent_at` + `revoked_at`), `EmergencyContact` (nama, nomor E.164, `consent_at`), `PlanExercise` yang terpisah dari katalog `Exercise`, `ScheduledSession`, `ExerciseLog` dengan status selesai/tidak bisa/ditunda dan `reported_by`, `Feedback`, `TherapistReview`, `push_tokens`, `devices`, `audit_logs` append-only, dan `envelope_version` di sesi. `AGENTS.md` menulis "Keep Exercise (catalog) separate from PlanExercise". Kalau `SafetyEnvelope` menempel ke `Exercise` katalog, batas menjadi global dan bukan per pasien per latihan, yang melanggar hard rule "real limits come from the therapist, per patient, per exercise". Tanpa `envelope_version`, terapis tidak bisa melihat batas yang berlaku saat event terjadi setelah batas diubah.

**K4. Sumber envelope untuk HP tidak dirancang.** F3 hanya menyebut ingestion dari HP dan `/screen` membaca. Tidak ada alur sebaliknya: HP mengambil program dan envelope dari backend (dossier: `GET /v1/me/bundle?since=versi`, cache berversi, "envelope yang dipakai sesi = versi terakhir yang tersimpan lokal"). FACT: sekarang envelope datang dari relay `config`. Selama dua jalur itu hidup berdampingan, tidak jelas mana yang menang, dan batas terapis di backend bisa tidak pernah sampai ke HP.

**K5. Ingestion tidak idempoten dan tidak offline-aware.** Dossier (Online atau offline): outbox di HP dengan `clientId`, `POST /v1/sync` batch ≤ 100 dengan `Idempotency-Key`, server upsert by `clientId`. FACT: `SessionSummary` sudah punya `id` dari klien dan Dexie sudah dipakai (`src/lib/db.ts`), tetapi flag `syncedAt` saat ini berarti "laptop sudah menerima" (alur `sessions-ack` di `messages.ts`), bukan "backend sudah menerima". F3 tidak menyebut idempotensi, retry, atau perubahan arti `syncedAt`. Hasilnya: sesi ganda atau hilang saat sinyal putus-nyambung.

**K6. Dua sumber kebenaran untuk riwayat sesi.** FACT (`docs/TESTING.md`, bagian History + transfer): catatan terapis yang ditulis di laptop tetap ada saat HP mengedit `difficulty` atau `note`; sinkronisasi saat ini di-upsert berdasarkan id sesi lewat relay. Setelah F3 ada IndexedDB di HP, IndexedDB di laptop, dan Postgres. Aturan penggabungan field yang diedit dua pihak (note pasien, catatan terapis, `reportedBy`) belum ada.

**K7. Eskalasi tanpa timer yang tahan restart.** Dossier menaruh `escalate-l3` dan `send-push` di Redis/BullMQ karena "timer harus tetap jalan walau server restart" dan "FCM bisa lambat/gagal; retry dengan backoff". F4 hanya L2 + push, tetapi retry push, batas push per sesi, dan arti "ack membatalkan timer" tetap butuh state yang bertahan. `server.mts` adalah satu proses Node; timer di memori hilang saat restart atau deploy. Kalau retry tidak ada, satu kegagalan FCM sama dengan alert yang tidak pernah terkirim, tanpa jejak.

**K8. Dua jalur real-time tanpa kontrak.** Dossier memilih Socket.IO dengan room `patient:{id}` dan `therapist:{id}` dan cek relasi saat handshake. FACT: repo punya relay `ws` buatan sendiri dengan kode ruang 4 digit (alasan dan batasan di komentar `server.mts`). Rencana tidak menyebut apakah relay dipertahankan, diganti, atau hidup berdampingan dengan backend. Lihat S1 untuk akibat keamanannya.

**K9. Docker (F5) bentrok dengan custom server.** FACT: `custom-server.md` di dokumentasi Next menyebut mode `output: "standalone"` tidak melacak file custom server dan keduanya tidak bisa dipakai bersama. `server.mts` dijalankan Node langsung dengan type stripping (`docs/NOTES.md` M0: hanya sintaks "erasable", `constructor(private x)` crash) sedangkan `packageManager` adalah Bun. Image Docker perlu runtime Node versi yang mendukung `.mts` (NOTES menyebut Node 26) plus `node_modules` penuh. Semua modul yang diimpor `server.mts` untuk ingestion/ws harus lolos aturan erasable dan memakai ekstensi `.ts`.

**K10. `cacheComponents: true` di `next.config.ts` berinteraksi dengan auth berbasis cookie.** ASSUMPTION (belum saya baca detailnya): dengan Cache Components, akses cookies/headers di halaman butuh penanganan dinamis, dan kesalahannya baru muncul saat `next build`. `AGENTS.md` memerintahkan membaca `node_modules/next/dist/docs/` sebelum menulis kode; sebaiknya itu dijadwalkan sebelum F1.

**K11. Tidak ada riset pengguna di balik backend.** `AGENTS.md` (Not validated yet): belum ada wawancara terapis atau keluarga, dan belum terbukti terapis mau memakai dashboard. Open decisions yang berdampak langsung pada schema belum dijawab: apakah caregiver L1 masuk MVP, siapa yang memberi persetujuan bila pasien tidak mampu, ukuran dan keahlian tim, platform akhir. Membuat schema sekarang memaksa jawaban atas pertanyaan yang `AGENTS.md` larang diasumsikan ("do not assume an answer").

## 3. Risiko keamanan (OWASP)

**S1. Relay WebSocket tanpa autentikasi dapat menyuntikkan batas keselamatan dan breach palsu (OWASP API1 BOLA, API2 Broken Authentication).** FACT (`server.mts`, `rooms.ts`, `protocol.ts`): endpoint `/ws` menerima siapa saja; ruang diidentifikasi oleh 4 digit (`ROOM_CODE = /^\d{4}$/`, 10.000 kemungkinan) yang dibuat dengan `Math.random`; tidak ada rate limit tebakan; `rooms.relay` meneruskan teks apa adanya ke semua anggota ruang; tidak ada pengecekan `Origin` saat upgrade. Siapa pun yang menebak atau memindai kode bisa bergabung sebagai `screen`, mengirim `config` dengan `maxAngleDeg` besar ke HP pasien, atau bergabung sebagai `phone` (HP lama diusir) dan mengirim telemetri dan `breach` palsu. Di prototype itu wajar; begitu data masuk ke backend dan memicu alert, jalur ini menjadi vektor sensor palsu (dossier, tabel Ancaman). Dossier meminta handshake membawa access token dan cek relasi sebelum join room. Kendala teknis: `WebSocket` di browser tidak bisa mengirim header `Authorization`, dan token di query string melanggar "tidak ada data pribadi di URL" (dossier, lapis 3 Transport); jalur token untuk ws belum dirancang. Selain itu `ws` secara default menerima pesan hingga 100 MiB per frame (ASSUMPTION dari perilaku default library; belum dicek di versi 8.23), tanpa `maxPayload` di `server.mts`.

**S2. Token invite caregiver.** Dossier (Autentikasi): kode acak panjang, sekali pakai, kedaluwarsa, disimpan sebagai hash, dibatasi jumlah percobaan; rate limit pada kode undangan. Rencana hanya menulis "sekali pakai". Celah yang perlu ditutup: (a) token disimpan plaintext di `CaregiverInvite` berarti dump DB atau log membocorkan undangan aktif; (b) "sekali pakai" harus atomik, misalnya satu `UPDATE ... WHERE used_at IS NULL AND expires_at > now()` yang dicek jumlah barisnya, kalau tidak dua request bersamaan sama-sama berhasil; (c) tanpa batas percobaan per IP dan per akun, kode pendek bisa dibrute-force; (d) pesan error yang berbeda untuk "tidak ada", "kedaluwarsa", dan "terpakai" membocorkan status; (e) tautan atau QR undangan yang membawa token di query string tercatat di log akses, riwayat browser, dan header Referer. Kode ruang 4 digit di `rooms.ts` jangan dijadikan pola.

**S3. Peran di `user_metadata` Supabase dapat diubah pengguna sendiri (OWASP API3 BOLA/Mass Assignment, API5 BFLA).** ASSUMPTION (perlu dicek di dokumentasi Supabase): `user_metadata` dapat ditulis klien lewat `auth.updateUser`, sedangkan `app_metadata` hanya oleh service role. Dossier (Ancaman) sudah menyebut contoh persis ini: kirim `"role":"therapist"` saat update profil. Jika F1 menyimpan peran di `user_metadata`, atau mengambil `role` dari body saat sign-up, pengguna bisa menjadikan dirinya terapis. Rencana juga tidak menjawab siapa yang boleh mendaftar sebagai terapis: sign-up terbuka berarti siapa pun dapat mendaftarkan "pasien", membuat invite, dan menetapkan batas gerak. Dossier tidak membahas verifikasi terapis; itu pertanyaan terbuka.

**S4. Tabel Prisma di schema `public` Supabase dapat terekspos lewat PostgREST.** ASSUMPTION (perilaku Supabase yang perlu dikonfirmasi): Supabase membuka REST API otomatis untuk schema `public`, diakses dengan anon key yang memang dikirim ke browser (`NEXT_PUBLIC_*`). Tabel yang dibuat lewat migrasi Prisma tidak otomatis memakai Row Level Security. Prisma terhubung sebagai role Postgres yang melewati RLS, jadi Prisma tidak menunjukkan masalahnya dan semua tes Prisma lulus. Akibat yang perlu dibuktikan sebelum pakai data nyata: data kesehatan terbaca oleh siapa pun yang memegang anon key. Rencana tidak menyebut RLS, pencabutan hak role `anon`/`authenticated`, atau menonaktifkan Data API.

**S5. Service role key.** Kunci service role melewati RLS dan memberi akses penuh. F0 menyiapkan "helper Supabase"; risiko: helper admin diimpor dari Client Component (tidak berprefiks `NEXT_PUBLIC_`, tetapi bundling bisa gagal diam-diam atau malah error di build tanpa jelas), atau dipakai di route handler biasa sehingga tiap bug otorisasi menjadi akses penuh. Rencana tidak menyatakan dimana service role boleh dipakai. FACT tambahan: `.gitignore` memuat `.env*`, yang juga mengabaikan `.env.example`. Deliverable F0 `.env.example` tidak akan ter-commit kecuali ada pengecualian (`!.env.example`); tim berikutnya tidak akan melihat daftar variabel, dan ada godaan menyalin `.env` asli. Dossier (Operasional): secret di `.env` server, bukan di repo, dan konfigurasi divalidasi saat start; rencana belum menyebut validasi env.

**S6. Validasi payload dari HP (OWASP API3, API4 Unrestricted Resource Consumption, API6).** FACT: `SessionSummary` (`src/lib/rehab/summary.ts`) memuat `trace` (array pasangan angka sekitar 1500 titik per 5 menit), `repList`, `breaches`, `note` bebas, `deviceId`, `deviceLabel`, `battery`, `config` dan `reportedBy`. Semuanya dikirim klien. Tanpa skema ketat, batas ukuran, dan batas panjang string: (a) tabel membengkak atau request besar menghabiskan memori; (b) `startedAt` dan `endedAt` memakai jam HP (komentar "wall clock of the phone"), jadi urutan, durasi, dan batas waktu eskalasi tidak bisa dipercaya; waktu server harus dicatat terpisah; (c) `reportedBy` ditulis klien, sehingga caregiver dapat menandai catatan sebagai "patient"; server harus menurunkannya dari identitas login, bukan body; (d) `patientId` dan `role` tidak boleh dari body (mass assignment); (e) `config.envelope` di dalam ringkasan adalah klaim HP tentang batas yang dipakai; server harus membandingkan dengan envelope versi tersimpan, bukan menyimpannya sebagai kebenaran, kalau tidak terapis melihat batas yang tidak pernah ia tetapkan; (f) `breach` level 2 tanpa sensor nyata dapat membuat alert palsu; dossier meminta batas push per sesi, `clientId` idempoten, dan rate limit endpoint event.

**S7. Kebocoran lewat push dan log.** Dossier (lapis Operasional): log tanpa data kesehatan; contoh isi push "Pak Budi melewati batas". Teks push muncul di layar kunci HP caregiver dan lewat Google/Apple; nama pasien dan fakta bahwa ia sedang latihan rehabilitasi adalah data kesehatan. Rencana tidak menetapkan isi payload FCM minimum (misalnya hanya "Ada peringatan di Rehat", detail setelah login). Logger `console.log` default juga tidak merekam body; perlu aturan agar error handler tidak mencetak payload sesi.

**S8. Audit log dan hak DB.** Dossier: `audit_logs` append-only tanpa UPDATE/DELETE dan "user DB aplikasi tanpa hak DDL". Rencana tidak punya entitas `AuditLog` dan memakai satu `DATABASE_URL`. ASSUMPTION: pada Supabase koneksi default adalah role dengan hak luas; migrasi dan runtime perlu role berbeda. Tanpa itu, SQL injection atau bug di satu route dapat mengubah atau menghapus jejak akses data pasien.

**S9. Sesi dan revokasi.** Dossier: access token 15 menit, refresh berotasi dengan deteksi reuse yang mencabut semua sesi, terapis bisa mencabut device. ASSUMPTION: Supabase Auth punya rotasi refresh token dan deteksi reuse sendiri, tetapi perilaku persisnya (masa tenggang reuse, umur JWT bawaan, pencabutan JWT yang sudah terbit) berbeda dari dossier dan belum dicocokkan. Revokasi caregiver harus ikut memutus koneksi ws yang sedang terbuka dan menghapus token push; rencana F1 tidak menyebut keduanya.

## 4. Ketidakcocokan dengan dossier yang berisiko (medis, klaim aman, data kesehatan)

**M1. Nilai default atau seed yang tampak seperti batas klinis.** Hard rule `AGENTS.md`: "Never invent clinical thresholds". FACT: `src/lib/rehab/defaults.ts` berkomentar "CONTOH, bukan nilai klinis" untuk `EXAMPLE_ENVELOPE` (90°, 120°/s, 300 ms). Seed F0 dan schema Prisma yang memuat `@default(90)` atau baris seed dengan angka itu menjadikan contoh sebagai data di tabel `SafetyEnvelope`, yang tidak dapat dibedakan dari batas yang ditetapkan terapis. Risiko: pasien nyata mendapat batas yang tidak pernah ditetapkan siapa pun, dan tampil di UI sebagai "dari terapis". Kolom envelope seharusnya tidak punya default dan baris seed harus bertanda contoh. Validasi server pada rentang angka boleh sebagai pemeriksaan kewajaran, tetapi tidak boleh memotong atau mengganti angka terapis.

**M2. Kata "aman" atau "bahaya" di schema, enum, push, dan UI.** Hard rule: "Dangerous movement = whatever the therapist's safety envelope says. The app does not decide what is safe", dan alert diposisikan "berdasarkan batas dari terapis" karena risiko regulasi alat kesehatan (dossier, tabel Risiko). Entitas `Alert` dan `BreachEvent` memunculkan keputusan penamaan: kolom seperti `isDangerous`, `severity`, `safe`, atau teks push "gerakan berbahaya" menjadi klaim medis. Nama yang sesuai aturan mengacu pada batas ("melewati batas yang ditetapkan terapis"). Biome dan tsc tidak memeriksa ini.

**M3. Persetujuan (consent) belum dimodelkan, dan pertanyaan terbuka dipaksa dijawab oleh schema.** Dossier: persetujuan tercatat untuk pasien atau wali, pendamping, dan kontak darurat, masing-masing dengan waktu. Alur `CareLink`: terapis mendaftarkan pasien, invite, caregiver mendaftar dan memasukkan kode, pasien (atau terapis bila pasien tidak mampu) menyetujui, aktif, dapat dicabut. `AGENTS.md` mencatat "siapa yang memberi persetujuan kalau pasien tidak mampu" sebagai keputusan terbuka. F1 menulis "persetujuan" tanpa tabel dan tanpa menentukan pihak yang menyetujui; kolom seperti `consentedBy` atau `approverRole` yang dipilih saat F0 sama dengan menjawab pertanyaan itu. Status `pending` harus berarti akses data nol, dan `revoked` harus berlaku seketika (lihat S9). Persetujuan pemrosesan data pasien sendiri (bukan hanya caregiver) juga belum ada di entitas.

**M4. Retensi, hak hapus, dan data kesehatan sebagai data spesifik.** Dossier (Keamanan, FACT yang dikutip dari UU PDP No. 27/2022 Pasal 4): data kesehatan adalah data pribadi spesifik; Rehat "memproses data berisiko tinggi sejak hari pertama". Praktik minimum di dossier: persetujuan tercatat, minimisasi, pasien dapat melihat data sendiri dan meminta penghapusan (soft delete lalu hapus permanen terjadwal), retensi ditetapkan dengan penghapusan otomatis, backup terenkripsi dengan uji restore. Rencana F0 sampai F5 tidak memuat kolom `deletedAt`, job pembersihan, kebijakan retensi, ekspor data pasien, atau penanganan backup yang masih menyimpan data yang sudah dihapus. Angka masa simpan memang keputusan pemilik dan bukan saya, tetapi ketiadaan mekanismenya di schema berarti menambahkannya nanti memerlukan migrasi data kesehatan yang sudah ada.

**M5. Lokasi data dan pihak ketiga.** Dossier merancang Postgres dan penyimpanan di VPS milik tim (Docker Compose, hanya port 443 terbuka, backup terenkripsi ke penyimpanan lain). Rencana memakai Supabase Auth cloud yang menyimpan email, hash password, dan identitas pasien, terapis, dan caregiver di pihak ketiga, dengan kredensial cloud diparkir. ASSUMPTION: pemilihan region dan perjanjian pemrosesan perlu dicek terhadap aturan transfer data pribadi lintas negara di UU PDP; dossier sendiri menyatakan "bukan nasihat hukum". Ketergantungan baru ini juga berada di jalur alert: ASSUMPTION bahwa proyek Supabase tier gratis dapat dijeda saat tidak aktif; bila benar, login dan alert gagal tepat pada saat dibutuhkan.

**M6. Tampilan yang bisa terbaca sebagai indikator pemulihan.** Hard rule: "Adherence (exercise completion %) is not a recovery indicator. Never show or name it as one." Dossier: "Tidak bisa" dan "ditunda" tidak boleh dihitung sebagai gagal. Rencana menamai entitas `AttemptSummary` dan menyiapkan `/screen` yang membaca dari backend, tetapi tidak memuat status "tidak bisa" atau "ditunda" (hanya ada di `ExerciseLog` dossier). Tanpa status itu, sesi yang tidak ada akan terbaca sebagai kegagalan. Grafik tren `maxAngleDeg` atau jumlah repetisi dari waktu ke waktu mudah terbaca sebagai kemajuan pemulihan; aturan melarang diagnosis dan AI recovery score (daftar OUT di `AGENTS.md`). Perlu dipastikan tampilan hanya melaporkan angka mentah dan terpisah dari penilaian klinis.

**M7. Kegagalan jaringan dan "tidak dipantau = tidak aman".** Dossier (tabel Offline): alert L2 tidak terkirim saat offline, dan app harus menampilkan nomor pendamping beserta tombol telepon. FACT: F4 hanya menyebut push FCM. Tidak ada rancangan untuk kasus POST event gagal atau FCM tidak sampai: apa yang dilihat pasien, apakah latihan tetap dijeda, dan apakah UI berhenti mengklaim "pendamping sudah diberi tahu" sebelum ack server. Klaim terkirim yang keliru lebih buruk daripada tidak ada klaim.

**M8. Kontak darurat dan L4 hilang dari lingkup.** `AGENTS.md` (MVP IN): "linking with invite + consent (emergency contact at minimum)". Rencana menunda WhatsApp L3 dan tidak memuat entitas `EmergencyContact`, sehingga MVP minimum yang dikunci dossier tidak terpenuhi walau L3 diparkir. Nomor telepon kontak darurat adalah data pribadi dengan `consent_at` sendiri. L4 (arahkan ke layanan darurat setempat, tanpa saran medis otomatis) juga tidak disebut.

**M9. Minimisasi data: `trace` dan metadata perangkat.** Dossier dan `AGENTS.md`: simpan ringkasan dan event, bukan raw stream. FACT: `summary.ts` menyimpan `trace` turunan 5 Hz (sekitar 20 KB per 5 menit), `battery`, `deviceLabel`, dan `deviceId`. Apakah deret waktu sudut ini "ringkasan" atau data kesehatan yang lebih rinci dari yang dibutuhkan belum diputuskan; rencana F3 "ingestion ringkasan" tidak menyatakan field mana yang dikirim ke server. Mengirim seluruh `SessionSummary` apa adanya adalah default yang paling mudah dan paling melanggar minimisasi.

**M10. Klaim akurasi.** Dossier: laporkan error terukur tim sendiri, bukan angka dari paper; uji pada orang sehat tidak membuktikan apa pun untuk pasien stroke. Backend yang menyimpan breach event sebagai catatan keselamatan memberi kesan sensor ponsel sudah tervalidasi. FACT: validasi baru berupa alat di tab "Validasi" (`docs/NOTES.md` M2); saya tidak menemukan angka error terukur di `NOTES.md`. Tampilan dashboard sebaiknya memuat penafian yang sama dengan dossier.

## 5. Hal yang tidak akan tertangkap CI

FACT dasar: tidak ada direktori `.github` di repo, `package.json` hanya punya `test` (`bun test`, saat ini 5 file tes pure-TS di `tests/`) dan `lint` (`biome check`). CI di F5 baru dibuat dan hanya menangkap apa yang ada tesnya.

1. **Tes 403 BOLA.** Dossier: "caregiver A meminta pasien B harus 403, tes ini harus selalu lulus". Tes ini butuh DB dan dua akun. F0 "tanpa DB hidup" dan CI tanpa service Postgres tidak akan menjalankannya; tes dengan Prisma yang di-mock lulus walau SQL dan policy salah.
2. **Paparan PostgREST dan RLS (S4).** Tidak terlihat oleh Prisma, tsc, biome, atau `next build`. Hanya pemeriksaan langsung ke endpoint REST Supabase dengan anon key yang menemukannya.
3. **Kebocoran service role key ke bundle klien (S5).** `next build` tetap sukses; perlu pencarian string di `.next/static` atau aturan lint khusus.
4. **`.env.example` yang tertelan `.gitignore` (S5).** CI tidak gagal bila file itu tidak ada kecuali ada langkah yang memeriksanya.
5. **Peran di `user_metadata`, sign-up terbuka sebagai terapis (S3).** Hanya tes integrasi terhadap Supabase sungguhan yang menangkapnya.
6. **Race invite sekali pakai (S2).** Butuh tes konkurensi terhadap DB nyata; tes unit sekuensial lulus.
7. **Kata "aman" atau "berbahaya" dan klaim medis di UI, push, dan nama kolom (M2, M6).** Tidak ada linter untuk aturan `AGENTS.md`; hanya tinjauan manusia atau pemeriksaan teks khusus.
8. **Nilai seed atau default yang terbaca sebagai batas klinis (M1).** Tes lulus dengan nilai apa pun.
9. **Retensi dan hapus permanen (M4).** Job cleanup dan backup yang masih memuat data terhapus tidak diuji oleh unit test biasa; salah paham baru ketahuan saat ada permintaan hapus.
10. **FCM end-to-end (F4).** Kredensial FCM diparkir, jadi F4 hanya bisa lulus dengan mock. Tidak teruji: pengiriman saat tab tertutup atau HP terkunci, latensi (dossier T1: beberapa detik), perilaku iPhone (P5), isi push di layar kunci (S7). Label "F4 selesai" hanya berarti kode terbentuk, bukan bahwa alert sampai.
11. **Perilaku di HP nyata.** `devicemotion`, izin iOS, wake lock, sensor lost lalu pause, getar dan suara cue: semuanya dicek manual lewat `docs/TESTING.md` di Android dan iPhone dan tidak bisa diotomasi di CI. Perubahan edge untuk pause saat breach (P2) termasuk di sini.
12. **Migrasi terhadap Postgres terkelola dan pooler (P7), dan perbedaan role runtime vs migrasi (S8).** Tes dengan Postgres lokal di CI tidak menirunya.
13. **Image Docker yang berhasil di-build tetapi gagal start (K9).** Node harus mendukung `.mts`, `node_modules` penuh dibutuhkan, dan env tervalidasi saat start; `docker build` lulus walau kontainer langsung mati. Perlu smoke test `/healthz` yang dijalankan di CI.
14. **`next build` dengan `cacheComponents` dan auth berbasis cookie (K10).** Build gagal hanya setelah halaman auth ditambahkan; CI F5 menangkapnya, tetapi baru di akhir.
15. **Selisih jam HP dan server (S6b).** Tes dengan jam seragam tidak mengungkapnya.
16. **Sebagian besar kebutuhan keamanan dossier di luar kode:** HTTPS/WSS dan HSTS, rotasi secret saat anggota keluar, backup terenkripsi dan uji restore, pembatasan hak DB. Ini kebijakan operasional, bukan hasil tes.
